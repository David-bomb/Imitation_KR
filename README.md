# GPU Lab — симулятор датацентра

Локальное приложение на Python 3.13: задачи ожидают в FIFO-очереди, занимают GPU и освобождают их после заданного количества тиков. В ноде до восьми видеокарт.

## Запуск

Требуется Python 3.13 с Tkinter. Из корня репозитория в PowerShell:

```powershell
py -3.13 -m venv venv
& .\venv\Scripts\python.exe -B .\main.py
```

Окружение создаётся один раз; если папка `venv` уже есть, достаточно команды запуска. Установка библиотек не нужна: Tkinter, TOML-парсер и unittest входят в Python. Конфигурация загружается рядом с main.py независимо от текущей папки.

## Использование

1. Укажите длительность тика в миллисекундах и количество GPU, нажмите «Старт».
2. Введите название задачи, базовую длительность в тиках и запрос GPU, нажмите «В очередь».
3. Красная заливка означает занятую карту, светлая — свободную. Контур не меняет цвет. Наведение показывает задачу и оставшиеся тики.
4. Используйте вкладки очереди, выполняющихся и завершённых задач. Колонка «Нода: GPU» показывает распределение, например «1: 8, 3: 1».
5. Для автоматической нагрузки включите генератор. После изменения полей нажмите «Применить настройки».

«Пауза» останавливает логическое время. «Один тик» доступен на паузе. После «Продолжить» следующий тик наступает через полный интервал.

«Новая симуляция» очищает задачи и возвращает экран настройки. Закрытие приложения также теряет состояние. Настройки сессии не записываются в файл.

Всегда четыре ноды в ряду; прокрутка колесом или полосой справа. При 250 GPU последняя нода содержит две карты, остальные шесть мест отмечены крестиком.

## Сортировка таблиц

В каждой вкладке по умолчанию включена сортировка по возрастанию ID: старые задачи сверху. Нажатие на заголовки ID, GPU, «Ост./всего», «Старт» и «Финиш» переключает состояния: без сортировки → по возрастанию ↑ → по убыванию ↓ → без сортировки. Поэтому первый клик по уже активному ID переключает его на убывание.

В одной вкладке активен только один столбец; выбор другого отключает предыдущий. Каждая вкладка хранит свою настройку до новой симуляции. Сортировка сохраняется при тиках и появлении новых задач.

Значения сравниваются как числа. «Ост./всего» сортируется по оставшимся тикам, отсутствующие даты остаются внизу. Без сортировки показывается исходный порядок: очередь — по поступлению, выполняющиеся — по запуску, завершённые — по завершению. Сортировка таблицы не меняет FIFO и распределение GPU.

## Распределение и время

Сначала задача получает полные группы по восемь GPU в пустых нодах. Остаток помещается в одну частично занятую ноду, если возможно, иначе — в одну пустую. При фрагментации используется минимальное число нод, затем минимальное число новых пустых нод.

Для запроса 9 GPU при наличии пустой ноды и занятых со свободными 5 и 4 GPU результат — **8 + 1**. Если пустой ноды нет — **5 + 4**.

За тик запускаются все помещающиеся задачи подряд. Первая непомещающаяся задача блокирует следующие. Названия могут повторяться: задачи различаются по ID.

Задача на один базовый тик в одной ноде, запущенная на тике №1, завершится на №2. Её GPU можно назначить следующей задаче на №3. Ожидание в очереди не уменьшает длительность.

## Штраф за межузловой обмен

После размещения длительность равна `ceil(time_ticks * (1 + node_penalty * (n - 1)))`, где `n` — число нод именно этой задачи. По умолчанию `node_penalty = 0.5`: на одной ноде штрафа нет, на двух время умножается на 1,5, на трёх — на 2. Например, 20 базовых тиков превращаются в 20, 30 или 40. Результат округляется вверх до целого тика; один базовый тик на двух нодах занимает два тика.

Исходная длительность сохраняется. В очереди «Ост./всего» показывает базовое время; после назначения — оставшееся и полное время со штрафом. Подсказка занятой GPU также показывает базовое время, добавленные тики и число нод. Штраф определяется один раз при запуске; ожидание в очереди его не увеличивает. `tick_ms` управляет только темпом показа.

Коэффициент задаётся в config.toml до запуска программы, должен быть конечным неотрицательным числом. Значение 0 отключает штраф. Это приближённая модель коммуникационных затрат: она не учитывает объём передаваемых данных, пропускную способность сети и конкуренцию за сеть. Коэффициент не является универсальной характеристикой реального оборудования.

## Настройки

Файл config.toml:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| tick_ms | 1000 | Интервал между тиками, мс |
| gpu_count | 256 | Общее количество GPU |
| node_penalty | 0.5 | Добавка к базовому времени за каждую ноду сверх первой |
| generator.enabled | false | Автогенератор |
| generator.probability | 0.35 | Вероятность одной новой задачи за тик |
| generator.time_min / time_max | 1 / 20 | Включительные границы базовой длительности |
| generator.gpu_min / gpu_max | 1 / min(32, gpu_count) | Включительные границы запроса GPU |
| generator.seed | не задан | Целое число для воспроизводимого потока |

По умолчанию gpu_max не записан в файле и рассчитывается по размеру кластера. При уменьшении кластера через начальный экран диапазон генератора ограничивается его ёмкостью; действующие значения видны в панели.

Вероятность 0 запрещает поступления, 1 создаёт задачу каждый тик. Длительность и запрос выбираются равномерно. Для повторения сценария используйте одинаковые настройки, seed и последовательность действий. Изменение seed начинает новый случайный поток; применение остальных настроек не сбрасывает его.

Тик — целое число от 1 до 2147483647 мс, GPU и длительность — положительные целые. Запрос не может превышать ёмкость кластера. Малый интервал ограничивается скоростью обработки и отрисовки: приложение не является таймером реального времени и не догоняет задержку скрытыми тиками.

Некорректный config.toml вызывает сообщение при запуске; исправьте файл и запустите приложение заново.

## Проверки

Из корня репозитория в PowerShell:

```powershell
& .\venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

Тесты Tk требуют графического сеанса. При отсутствии дисплея они пропускаются; проверяйте итоговое число пропусков.
